## 2. Version, migration carrier and lifecycle

### 2.1 Explicit successor and native G0 migration

Create a separately resolvable `diagram-view-schema@2`. Its Pin uses id `diagram-view-schema`, version string `2`, and the measured digest from the existing governing path. Its JSON Schema `$id` is `engram:diagram-view-schema/2`. This version changes neither semantic profile versions, `ViewDocument.revision`, nor `diagram-presentation@1`.

Retain the complete @1 JSON Schema value, `$id`, Pin and digest. Existing `DIAGRAM_VIEW_SCHEMA` and `GOVERNED_SCHEMAS["diagram-view-schema"]` (`diagram-schemas.ts:203,255–259`) retain their version-1 meaning. Engram must provide explicit version-and-digest resolution and enumeration for both versions without shadowing the alias. Unknown versions, mismatching digests and unavailable bytes refuse without fallback to latest (G0:83,1159).

The transformation in §4 is a **G0 migration in the sense of G0:177**: explicit, retaining the original and refusing unknown majors. Under catalog carriers (i) and (ii) in §8, it is referenced through `migrationRef` (177), `lineage.migrations` (174) and the payload's `migrations` field (724). Under carrier (iii), no catalog record or payload field carries it; the outside-catalog provenance rule in §5.2 applies. For an admitted record, G0:176 carries `supersededBy`; G0:186 defines `deprecate(id, version, reason)` and `supersede(old, new, migrationRef)`. A superseded record pairs its successor pin with the migration reference. A deprecated record may name the successor while staying deprecated. Frozen line 1011 also includes `migrationRef?`. These fields reference the migration; they do not embed its executable body into schema/profile content.

**No G0 mapping-file arm is used.** G0:531–552 closes `MappingEntry` to rename, endpoint, type, vocabulary, cardinality, hierarchy and severity; none expresses copying a storage key into an absent field with conflict refusal. This specification neither adds an arm nor encodes this transformation as a rename. The D-B7 analogy (G0:496,1402) is limited to versions plus explicit transformation, no overlay; its TRK/H2A composition prohibition is not extended to diagram profile migrations.

The native migration mechanism does not answer how a standalone schema is catalogued, how migration refusals are encoded, or how the uncatalogued @1 draft changes lifecycle. Those remain the owner + Engram questions in §8. No catalog entry or new union arm is inferred here.

### 2.2 @1 lifecycle: two choices, no assumed deprecation

At the inspected revision @1 is governed code data without a standalone catalog record. A draft outside admission has no catalog entry (G0:180); deprecation is a state change on a catalog record (198). Publishing a known off-spec schema just to deprecate it is not automatically admissible.

Neither option is selected by this specification. Both retain exact-pin resolution and immutable @1 bytes. Do not add changed content, stack pins or lineage under cover of a deprecation-only transition. Any applicable migration/succession linkage must be established through the chosen carrier and proper lifecycle operation. Do not silently substitute `supersede` for the owner's lifecycle choice.

### 4.3 Empty labels and occurrence disambiguation

Already DS-conforming data using them can be adopted directly under an exact @2 Pin without rewriting either field. The strict @1 migration leaves occurrence disambiguation absent. Shape conversion does not promise to make every legacy view DS-valid. Direct @2 adoption still requires DS validation, including empty-list refusal (§3.2).
