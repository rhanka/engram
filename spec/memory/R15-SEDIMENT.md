## 1. The Engram-First Principle

### 1.1 Primary Ingestion and Serialization Front
`engram` is the primary ingestion front of the entire runtime architecture (`« Engram doit etee en premier front pour recup les donnes de session avant track, avec des analystes »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:19]`). Every session datum enters `engram` before any downstream consumer acts on it: speech turns (`tour de parole`), tool execution results, owner decisions (both project decisions and harness decisions), formal mandates, and harness rules (`« Attention car le premier rang doit etre engram (enregistrement pkur serialisarkkn eg tour de parole + regles + conrrole track si possible par agent). »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:15]`; `[FACT: memory-dossier/owner-r8/comments-2026-11-07.md:19,28]`).

`engram` is also the sole serialization producer (`D34=engram`, replayed by the `Track` control before merge) and canonical authority (`D28=engram`) `[FACT: memory-dossier/owner-r15/answers-2026-11-08.compact.md:5]`. It serializes committed artifacts by domain into Git repositories and Pull Requests:
1. **Specifications and memory cards** (`spec/`; cards under the existing `.engram/` application directory, card layout `proposed`) `[FACT: spec/SPEC_LIVE_GIT_INDEXING.md:64; memory-dossier/owner-r15/comments-2026-11-08.md:14]`.
2. **Project decisions and project event trails** (`Track` artifacts and `.track/` PR serializations, carrying both the event journal and a state snapshot, linked by fingerprint, per `D29=both`) `[FACT: memory-dossier/owner-r15/answers-2026-11-08.compact.md:5]`.
3. **Workspace and repository harness overlays** (committed per developer/workspace/repository on top of the `h2a` master harness, `proposed` `.h2a/` path: `« C est tres mauvais tu confonds bcp de concepts. Engram est la memoire et enregistre les decisions de harnais. H2a a le master harnais et chaque dev a sa surouche. Engram tien le premker rang et tout comme on serialise les spec du engram et le track on serialise la surcouche de chque workspace / repo qu on va aussi commiter »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:14]`).

### 1.2 Downstream Analysts Reading Engram
Downstream modules do not sit in front of `engram`; they operate as specialized **analysts** reading the `engram` graph (`« Track nest qu un modal d analyst et controle mais le harnais en est un autre et l agent dormant aussi... »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:19]`):
- **Track Analyst (project decisions, project events, and control):** Reads `engram` to structure project decisions, project event timelines, and realization state (`« Attention track c juste pour les decision et gestion d evenement projet. Engram doit etre la premiere etape in fine. »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:9]`) while maintaining live tracking with `engram` (`« trakc avec engram devra vraiment assurer un suivi live »` `[FACT: memory-dossier/owner-r10/suivi-direct-2026-11-07.md:5]`).
- **Harness Analyst (`h2a` rules, roles, and mandates):** Reads and updates `engram` to govern harness rules, workspace/repo overlays (`D31`), and the `h2a` role and activity ontology (`D16`). When no role is active, `h2a` proactively analyzes session activity in `engram` and proposes role and rule structures (`« Quand il n y a pas de role, h2a devrait etre proactif en analyse et proposition. »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:2]`).
- **Dormant Dreaming Agent (periodic resynthesis and long-term recall):** Resynthesizes session graphs on default cadences nightly (the owner's « daily »), weekly and monthly, and event triggers mid-day and context saturation (`« un processus dormant (dreaning agent) de resynthese de session sur une periode (daily, mi journee, a saturation du contexte) »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:3]`; `« J avais demandé daily. Donc jendirais comme j avais demande nighly weekly monthly par defaut. »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:11]`) to surface permanent knowledge forgotten in short-term execution (`« Le mode dreaming veenant rappelera des choses permanentes oubliees sur le court terme. »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:7]`).

### 1.3 Control and Extraction Posture
- **Control (`engram` + `Track`):** Control originates from both `engram` and `Track` (`« Donc part de engram - et de track »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:16]`). Control mechanisms may be implemented as a deterministic rules/decision engine (owner verbatim: `« api type jev/decison »`), a fast low-latency LLM, or an agent where warranted (`« L usage d agent en controle pour track iu engrame devrai etre possible mais potentiellement reposer plutot sur des api type jev/decison ou llm tres rapides. Je ne sais pas si ce seront des "agents" »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:15]`).
- **Extraction Pipeline:** Live extraction from session turns and tool outputs into the `engram` graph runs either through a permanent lightweight extraction LLM alongside the session or through the session LLM itself, evolving later toward specialized deep-learning extraction models (`« Il faut oeut etre en permanence un deuxiemme llm light d extraction ou reposer sur le llm de session pour les decisions a terme pkoi pas des modeles deeplearninf specialises. »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:19]`).

### 1.4 Context Replacement, Cluster-Mesh Federation, and Interface Layer
- **Durationless Contextual Graph Prompts:** The `engram` contextual graph replaces linear session history (`« La memoire graphe devrait remplacer le conexte en une forme de resumé a chaque etape c etait ma demande. »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:7]`). Each LLM prompt is independent and durationless, assembled from a contextual graph query to `engram` (carrying the formal `h2a` mandate as a primary fingerprint component `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:6]`), the query result, and the reprocessed output of the preceding step (`« Comme je disais precedemment un contexte de session devrait etre une requete contextuelle a la memoire + le resultat de la requete. L envoi au llm ne devrait pas envoyer de vieux contexte. »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:8]`). Raw text history remains queryable on demand through the memory graph `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:8]`.
- **Integral Cluster-Mesh Graph Sync and MCP Registry:** `h2a` accesses memory and exposes MCP tools exclusively through `sentropic/cluster-mesh` and its `mcp-platform` registry `[FACT: memory-dossier/owner-r9/r12-correction-2026-11-07.md:5; memory-dossier/owner-r11/mcp-correction-2026-11-07.md:5]`. Local and remote `engram` graphs synchronize integrally as database transactions and DB-cluster replication over `cluster-mesh` (`« De plus j ai demande un partage de graphe entre local et remote. Integral. Engram doit gere ca comme des transaction et synchro de cluster de db via cluster mesh. »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:10]`).
- **Interface and Input Layer (GitHub / Boards):** GitHub issues, PRs, and project boards are a human-machine interface (HMI) and external input layer—distinct from both `engram` (memory) and `Track` (project analyst/control)—capable of feeding external signals back into `engram` (`« Attention tu confonds l outil track la memoire e tun outil ihm pour interagir avec - gh pourra donner de l input c une autre layer »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:13]`).

### 1.5 Harness review and harness graphs (owner, 2026-11-08, relayed by the h2a conductor)
- `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:24]` « typiquement le harnais h2a devrait être revue a l'oree d'une audition multi repo (dreaming agent) la ou l'évolution du harnais devrait être pour le repo lui meme ». Settled principle: the h2a master harness is reviewed by the dreaming agent in a multi-repo audit; each repository's own harness overlay evolves in that repository (for example, the single-writer Track rule stays h2a-only).
- `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:25]` « une skill de harnais h2a pourrait être un graph » + « de meme pour les rôles h2a ». Settled principle: h2a harness skills and h2a roles are modelled as graphs in engram, in the h2a ontology (with D16).

## 3. Superseded Framings (Rejected in R15 — Do Not Reintroduce)

The following ten framings from the R11–R15 dossier are explicitly rejected by the owner and permanently retired `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:2-20; spec/memory/REQUEST_R16_MODELLING.md:9]`:

1. **Linear context accumulation and session rollover (`D19`, `D22`, `D23`, `kit:3340, 3559, 3611`):**
   - *Rejected framing:* Treating sessions as growing linear transcripts that periodically hit a token limit and undergo manual or automatic "session rollover" (`rollover=manual` / `inheritance=fingerprints` as linear handoff notes) `[FACT: memory-dossier/kit/src/memory-content-r11.json:3340,3559,3611]`.
   - *Why rejected:* It perpetuates linear memory anti-patterns (`« Ce faisant tu perennise de mauvais patterns de memoire lineraire. »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:7]`). Prompts must be durationless and independent of old transcript context, assembled at every step from a contextual graph query to `engram` (with the `h2a` mandate as primary fingerprint component) plus the reprocessed previous result `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:6-8]`.
2. **Track as the primary ingestion entry point (`D24`, `D32`, `kit:3668, 4100`):**
   - *Rejected framing:* Routing session events, admission requests, or state federation through `Track` first (`.track/events.jsonl` as front door, `request-state-federation=commands` via `Track`) before `engram` sees them `[FACT: memory-dossier/kit/src/memory-content-r11.json:3668,4100]`.
   - *Why rejected:* `engram` is the first front for all session data (`tour de parole`, tool results, decisions, rules); `Track` is downstream of `engram` and handles only project decisions, project events, and project control (`« Attention track c juste pour les decision et gestion d evenement projet. Engram doit etre la premiere etape in fine. Cette assertion me smeble tres mauvaiss »` and `« Engram doit etee en premier front pour recup les donnes de session avant track, avec des analystes - Track nest qu un modal d analyst et controle »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:9,19]`).
3. **« Agent » by default for memory and Track control (`D32`, `kit:4100`):**
   - *Rejected framing:* Assuming that every control, gating, or extraction loop inside `Track` or `engram` must be instantiated as an autonomous conversational "agent" `[FACT: memory-dossier/kit/src/memory-content-r11.json:4100]`.
   - *Why rejected:* Control from `engram` and `Track` can rely on a deterministic rules/decision engine (owner verbatim: `« api type jev/decison »`) or fast low-latency LLMs rather than heavyweight agents (`« L usage d agent en controle pour track iu engrame devrai etre possible mais potentiellement reposer plutot sur des api type jev/decison ou llm tres rapides. Je ne sais pas si ce seront des "agents" »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:15]`).
4. **Engram-only harness decisions without Git-committed workspace/repo overlays (`D31`, `kit:4048`):**
   - *Rejected framing:* Posing a binary choice between storing harness decisions only inside `engram` (`engram-only`) versus storing them in `.track/` (`track-only`), omitting the `h2a` master harness and per-workspace/repository Git overlays `[FACT: memory-dossier/kit/src/memory-content-r11.json:4048]`.
   - *Why rejected:* `engram` records all harness decisions in first rank, `h2a` owns the master harness, each developer/workspace/repo has an overlay (`surcouche`), and `engram` serializes each workspace/repo overlay to be committed into Git alongside specs and `Track` (`« C est tres mauvais tu confonds bcp de concepts. Engram est la memoire et enregistre les decisions de harnais. H2a a le master harnais et chaque dev a sa surouche. Engram tien le premker rang et tout comme on serialise les spec du engram et le track on serialise la surcouche de chque workspace / repo qu on va aussi commiter »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:14]`).
5. **The board fed directly from Track as a peer store (`D30`, `kit:4004`):**
   - *Rejected framing:* Treating project boards and GitHub (`board-source=live` / `pr` / `both`) as a direct projection of `Track` storage rather than a separate HMI/input tier `[FACT: memory-dossier/kit/src/memory-content-r11.json:4004]`.
   - *Why rejected:* It conflates `engram` (memory), `Track` (project analyst/control tool), and GitHub/boards (an HMI and external input layer that reads `engram` views and can also push inputs into `engram`) (`« Attention tu confonds l outil track la memoire e tun outil ihm pour interagir avec - gh pourra donner de l input c une autre layer »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:13]`).
6. **Worktrees as flat approved aliases (`D21`, `kit:3490`):**
   - *Rejected framing:* Treating git worktrees as flat path aliases (`worktree=alias`) without modelling them as derived graph entities `[FACT: memory-dossier/kit/src/memory-content-r11.json:3490]`.
   - *Why rejected:* Worktrees must be modelled in `engram` as Scion-like derived workspace entities (`« J ai demande un scion like et c est cette merde que j ai les donmees sont pas modelisees »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:5]`).
7. **Dreaming review capped at one session per week, or tied to milestones (`D25`, `kit:3731`):**
   - *Rejected framing:* Capping dreaming review proposals at one session per week or tying them only to milestones (`dream-review-cadence=weekly-milestones`) `[FACT: memory-dossier/kit/src/memory-content-r11.json:3731]`.
   - *Why rejected:* The owner requested default cadences nightly (the owner's « daily »), weekly and monthly (`« J avais demandé daily. Donc jendirais comme j avais demande nighly weekly monthly par defaut. »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:11]`).
8. **Session continuity posed as a choice between mandate only and fingerprint chain (`D22`, `kit:3559`):**
   - *Rejected framing:* Posing cross-session continuity as a binary choice between « Mandat seul » and « Chaîne d’empreintes » (`inheritance=fingerprints`) `[FACT: memory-dossier/kit/src/memory-content-r11.json:3559]`.
   - *Why rejected:* Continuity targets role consciousness, where the fingerprint is a contextual graph query in which the formal `h2a` mandate is a primary component (`« Le choix est mal posé et je me demande sur quelle base de spec les decisions sont prises. On dojt atteimdre une forme de conscience dans le role. L empreinte etant unenrequet graphe dans le quel le mandat eat un composant primaire. Donc de base je dirais c est pile entee les deux ce qu ej ai en tete »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:6]`).
9. **Context delivery reduced to a hook fallback for CLIs without in-turn injection (`D19`, `kit:3340`):**
   - *Rejected framing:* Treating context delivery on CLIs without in-turn injection as a shallow fallback (`hook-fallback=hybrid`: context at launch, then at the first governed read) `[FACT: memory-dossier/kit/src/memory-content-r11.json:3340]`.
   - *Why rejected:* `engram` replaces linear session context with a live contextual graph coupled with a dormant dreaming agent (`« Ca manque serieusement de profondeur. J ai demande que l un graph contextuel remplace le contexte. Et qu on ai un processus dormant (dreaning agent) de resynthese de session sur une periode (daily, mi journee, a saturation du contexte) »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:3]`).
10. **An R15 architecture shown without the design-system diagram model (`REQUEST_R16_MODELLING.md:9`):**
    - *Rejected framing:* Presenting the R15 architecture in plain Mermaid without the design-system diagram model (`engram.archi-mermaid/1`, `archi@1` / `archi-cards@1`) `[FACT: spec/memory/REQUEST_R16_MODELLING.md:9]`.
    - *Why rejected:* The owner refused an R15 without the design-system diagram model (`« Alors non r15 sans notre modele de diagramme design system c est non. Refais e tu mettencette synthese au sein du r14 qui devient le r15 »` `[FACT: spec/memory/REQUEST_R16_MODELLING.md:9]`).
