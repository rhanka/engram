## 1. The Engram-First Principle

### 1.1 Primary Ingestion and Serialization Front
`engram` is the primary ingestion front of the entire runtime architecture (`« […] Engram doit etee en premier front pour recup les donnes de session avant track, avec des analystes […] »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:19]`). Every session datum enters `engram` before any downstream consumer acts on it: speech turns (`tour de parole`), tool execution results, owner decisions (both project/production decisions and harness decisions), formal mandates, and harness rules (`« Attention car le premier rang doit etre engram (enregistrement pkur serialisarkkn eg tour de parole + regles + conrrole track si possible par agent). […] »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:15]`; `[FACT: memory-dossier/owner-r8/comments-2026-11-07.md:19,28,54]`).

`engram` is also the sole serialization producer (`D34=engram`, applying the `Track`-published template version, replayed by the `Track` application control before merge and blocking merge on discrepancy per `Point 1B`; `never repaired by engram` is `proposed, not decided by the owner` — source seat: `h2a`) and canonical authority (`D28=engram`, explicitly kept on `2026-11-14`) `[FACT: memory-dossier/owner-r15/answers-2026-11-08.compact.md:5; spec/memory/OWNER-DECISIONS-2026-11-14.md:22]`. It serializes committed artifacts by domain into Git repositories and Pull Requests:
1. **Specifications and memory cards** (`spec/`; cards under the existing `.engram/` application directory, card layout `proposed`) `[FACT: spec/SPEC_LIVE_GIT_INDEXING.md:64; memory-dossier/owner-r15/comments-2026-11-08.md:14]`.
2. **Project decisions and project event trails** (`Track` artifacts and `.track/` PR serializations applying the `Track`-published template version, replayed and accepted solely by `Track` control per `Point 1B`; `never repaired by engram` `proposed, not decided by the owner` — source seat: `h2a`; carrying both the event journal and a state snapshot linked by fingerprint per `D29=both`). All tracking events are managed in `engram` and explicitly connected to their `engram` source with zero isolated/unconnected `events.jsonl` module card (`« pardon mais 1. events doit être géré par engram. la sérialisation potentiellement via track je ne sais pas mais la c'est sûr qu'il n'y a aucune connexion a aucun module donc y a un pb »` `[FACT: memory-dossier/owner-r8/comments-2026-11-07.md:28; memory-dossier/owner-r15/answers-2026-11-08.compact.md:5; spec/memory/OWNER-DECISIONS-2026-11-14.md:22]`).
3. **Workspace and repository harness overlays** (committed per developer/workspace/repository on top of the `h2a` master harness; `.h2a/` Git directory layout `proposed, not decided by the owner` — source seats: `Fable`, `Carbon`, `h2a`: `« C est tres mauvais tu confonds bcp de concepts. Engram est la memoire et enregistre les decisions de harnais. H2a a le master harnais et chaque dev a sa surouche. Engram tien le premker rang et tout comme on serialise les spec du engram et le track on serialise la surcouche de chque workspace / repo qu on va aussi commiter »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:14; spec/memory/OWNER-DECISIONS-2026-11-14.md:25]`).

### 1.2 Downstream Analysts Reading Engram
Downstream modules do not sit in front of `engram`; they operate as specialized **analysts** reading the `engram` graph (`« […] Track nest qu un modal d analyst et controle mais le harnais en est un autre et l agent dormant aussi... a voir. […] »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:19]`):
- **Track Analyst (project decisions, project events, and control):** Reads `engram` to structure project decisions, project event timelines, and realization state (`« Attention track c juste pour les decision et gestion d evenement projet. Engram doit etre la premiere etape in fine. Cette assertion me smeble tres mauvaiss »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:9]`) while maintaining live tracking with `engram` (`« trakc avec engram devra vraiment assurer un suivi live »` `[FACT: memory-dossier/owner-r10/suivi-direct-2026-11-07.md:5]`).
- **Harness Analyst (`h2a` rules, roles, mandates, and decision routing):** Reads and updates `engram` to govern harness rules, workspace/repo overlays (`D31`), decision response routing (`owner-r8/comments-2026-11-07.md:54`, §1.3 below), and the `h2a` role and activity ontology (`D16`). When no role is active, `h2a` proactively analyzes session activity in `engram` and proposes role and rule structures (`« Quand il n y a pas de role, h2a devrait etre proactif en analyse et proposition. […] »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:2]`).
- **Dormant Dreaming Agent (periodic resynthesis and long-term recall):** Resynthesizes session graphs on default cadences nightly (the owner's « daily », local per `Point 3C`), weekly and monthly (remote cross-repository audit after sync per `Point 3C`), and event triggers mid-day and context saturation (placement `proposed, not decided by the owner` — source seats: `Fable`, `Carbon`) (`« […] un processus dormant (dreaning agent) de resynthese de session sur une periode (daily, mi journee, a saturation du contexte) »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:3]`; `« J avais demandé daily. Donc jendirais comme j avais demande nighly weekly monthly par defaut. »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:11; spec/memory/OWNER-DECISIONS-2026-11-14.md:24]`) to surface permanent knowledge forgotten in short-term execution (`« […] Le mode dreaming veenant rappelera des choses permanentes oubliees sur le court terme. […] »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:7]`).

### 1.3 Control, Decision Routing, and Extraction Posture
- **Control (`engram` + `Track`):** Control originates from both `engram` and `Track` (`« Donc part de engram - et de track »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:16]`; `Point 5B` in `OWNER-DECISIONS-2026-11-14.md:26`). Control mechanisms may be implemented as a deterministic rules/decision engine (owner verbatim: `« api type jev/decison »`), a fast low-latency LLM, or an agent where warranted (`« […] L usage d agent en controle pour track iu engrame devrai etre possible mais potentiellement reposer plutot sur des api type jev/decison ou llm tres rapides. Je ne sais pas si ce seront des "agents" »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:15]`).
- **Decision Response Tool, First-Class `engram` Decision Entity, Async Stack, Swipe Review, and Non-Jargon Skill (`owner-r8/comments-2026-11-07.md:54`, correlated with `D3` and `D27`):** `h2a` provides a decision response tool capable either of triggering native CLI question tools directly (`askuserquestion` or equivalent) for urgent blocking decisions or of stacking non-blocking pending decisions (outside decision dossiers) asynchronously for review; `engram` models all decisions as first-class entities (`harness` vs `project/production` scope, urgent blocking vs async non-blocking posture, state, and scope-specific serialization destination); remote-control and local surfaces provide a swipe-through traversal mode across decisions and decision dossiers; and the decision skill enforces non-jargon prose, clear and complete context, and impact-and-risk explanations of candidate options (`« faudra prévoir dans h2a de mettre un tool de réponse, en capacité le cas échéant soit de trigger les différents outils de question des tools en direct (beosin urgent et bloquant askuserquestion ou autre tool des clis) ou stacking des decisions en attente non bloquante pour revue (les decision hors decision dossier) async, pour favoriser la prise de décision non bloquante. dans l'absolu les decision doivent être modélisées en tant que telles via engram (decision harnais, decision projet / production) et quand on sera en remote controle (ou meme en local) faut prevoir un mode de parcours des decision / decision dossier (en swipant d'un dossier a l'autre). le skill des decision devrait imposer une lecture non jargonneuse, avec un contexte clair et complex et une explication orientée impact et risque des différentes possibles options de décision. tracke ce besoin stp, et correle le au dossier memoire puisqu'engram doit stocker les decision. »` `[FACT: memory-dossier/owner-r8/comments-2026-11-07.md:54]`).
- **Extraction Pipeline:** Live extraction from session turns and tool outputs into the `engram` graph runs either through a permanent lightweight extraction LLM alongside the session or through the session LLM itself, evolving later toward specialized deep-learning extraction models (`« […] Il faut oeut etre en permanence un deuxiemme llm light d extraction ou reposer sur le llm de session pour les decisions a terme pkoi pas des modeles deeplearninf specialises. […] »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:19]`).

### 1.4 Context Replacement, Cluster-Mesh Federation, and Interface Layer
- **Durationless Contextual Graph Prompts:** The `engram` contextual graph replaces linear session history (`« La memoire graphe devrait remplacer le conexte en une forme de resumé a chaque etape c etait ma demande. […] »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:7]`). Each LLM prompt is independent and durationless, assembled from a contextual graph query to `engram` (carrying the formal `h2a` mandate as a primary fingerprint component `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:6]`), the query result, and the reprocessed output of the preceding step (`« Comme je disais precedemment un contexte de session devrait etre une requete contextuelle a la memoire + le resultat de la requete. L envoi au llm ne devrait pas envoyer de vieux contexte. […] »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:8]`). Raw text history remains queryable on demand through the memory graph `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:8]`.
- **Integral Cluster-Mesh Graph Sync and MCP Registry:** `h2a` accesses memory and exposes MCP tools exclusively through `sentropic/cluster-mesh` and its `mcp-platform` registry (`« R12 requis. Le h2a doit reposer sur cluster mesh pour la memoire. Ca se voit pas dans le diag d archi »` `[FACT: memory-dossier/owner-r9/r12-correction-2026-11-07.md:5]`; `« je veux juste être sûr que le mcp h2a passe bien par cluster mesh »` + `« repose bien sur le mcp registry de cluster mesh »` `[FACT: memory-dossier/owner-r11/mcp-correction-2026-11-07.md:5]`). Local and remote `engram` graphs synchronize integrally as database transactions and DB-cluster replication over `cluster-mesh` (`« De plus j ai demande un partage de graphe entre local et remote. Integral. Engram doit gere ca comme des transaction et synchro de cluster de db via cluster mesh. »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:10]`).
- **Interface and Input Layer (GitHub / Boards):** GitHub issues, PRs, and project boards are a human-machine interface (HMI) and external input layer—distinct from both `engram` (memory) and `Track` (project analyst/control)—capable of feeding external signals back into `engram` (`« Attention tu confonds l outil track la memoire e tun outil ihm pour interagir avec - gh pourra donner de l input c une autre layer »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:13]`).

## 3. Superseded Framings (Rejected in R15 — Do Not Reintroduce)

The following ten framings from the R11–R15 dossier are explicitly rejected by the owner and permanently retired `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:2-20; spec/memory/REQUEST_R16_MODELLING.md:9]`:

1. **Linear context accumulation and session rollover (`D19`, `D22`, `D23`, `kit:3340, 3559, 3611`):**
   - *Rejected framing:* Treating sessions as growing linear transcripts that periodically hit a token limit and undergo manual or automatic "session rollover" (`rollover=manual` / `inheritance=fingerprints` as linear handoff notes) `[FACT: memory-dossier/kit/src/memory-content-r11.json:3340,3559,3611]`.
   - *Why rejected:* It perpetuates linear memory anti-patterns (`« […] Ce faisant tu perennise de mauvais patterns de memoire lineraire. […] »` `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:7]`). Prompts are durationless and independent of old transcript context, assembled at every step from a contextual graph query to `engram` (with the `h2a` mandate as primary fingerprint component) plus the reprocessed previous result `[FACT: memory-dossier/owner-r15/comments-2026-11-08.md:6-8]`.
2. **Track as the primary ingestion entry point (`D24`, `D32`, `kit:3668, 4100`):**
   - *Rejected framing:* Routing session events, admission requests, or state federation through `Track` first (`.track/events.jsonl` as front door, `request-state-federation=commands` via `Track`) before `engram` sees them `[FACT: memory-dossier/kit/src/memory-content-r11.json:3668,4100]`.
